# Plan 08 — Dark/light theme toggle with reviewed font and icon colors

**Status: implemented** — see [plan-08-dark-light-theme-SUMMARY.md](plan-08-dark-light-theme-SUMMARY.md)
for what shipped, the three deviations (notably §5.6's icon transform, which had to be
replaced), and the macOS colour-scheme bug found during verification.
Design + implementation plan for
[issue #4](https://github.com/irfina/pagadmin3-javafx-reborn/issues/4) — a user-toggleable
Light / Dark / System theme, applied immediately across every window and dialog, persisted
across restarts, with every font color and icon reviewed for legibility in both themes
(WCAG AA: 4.5:1 body text, 3:1 graphics).

pgAdmin III 1.22 has no dark mode, so unlike previous plans there is no reference
behaviour to mirror — this is a deliberate, additive divergence. The constraint that *does*
carry over is visual fidelity: the light theme must stay pixel-for-pixel what it is today.

## 3. User story

```gherkin
Feature: Dark/light theme

  Scenario: Fresh install follows the OS
    Given no ~/.pgadmin3-javafx-reborn/preferences.json exists
    When the app starts on an OS set to dark mode
    Then every window opens dark; on an OS set to light, everything opens light
    And View > Theme shows "System" selected

  Scenario: Explicit switch, applied immediately everywhere
    Given the main window, a Query Tool, a Data Editor and Server Status are all open
    When the user picks View > Theme > Dark
    Then all four windows restyle at once — no restart, no per-window lag
    And a dialog opened afterwards (error alert, server dialog, backup dialog) is dark too

  Scenario: Selection persists
    Given the user picked Dark
    When the app is restarted
    Then it starts dark, and View > Theme shows "Dark" selected

  Scenario: System theme reacts to the OS live
    Given the theme is "System" and the OS is light
    When the OS switches to dark mode
    Then the app follows within the same session, without restart

  Scenario: Everything stays legible in dark mode
    Then SQL syntax highlighting keeps five distinguishable, readable token colors
    And the EXPLAIN diagram (canvas, node boxes, glyphs, connectors, labels) is legible
    And browser-tree and toolbar icons are the dark-set variants, legible on dark panels
    And body text meets 4.5:1 contrast, graphics/icons 3:1 (WCAG AA)

  Scenario: Light theme is unchanged
    When the user picks Light
    Then the app renders exactly as it did before this plan
```

## 4. Scope

**In scope**

1. `model/AppPreferences` — the dedicated preferences store the issue asks for:
   Jackson JSON at `~/.pgadmin3-javafx-reborn/preferences.json`, same shape as
   `ServerRegistry`. One field for now: `theme`.
2. `ui/ThemeManager` — single source of truth: selected theme property, effective
   light/dark resolution (System → OS), scene/dialog registration, live re-styling.
3. CSS refactor: `styles.css` keeps only structure + looked-up color tokens
   (`-app-*`); new `theme-light.css` / `theme-dark.css` define the tokens and (dark
   only) the Modena re-derivation.
4. Stylesheet centralization: all 7 `Scene` sites and all ~10 dialog sites route
   through `ThemeManager`.
5. `ExplainIcons` conversion from `Color` constants to CSS style classes, so glyphs
   restyle live with the theme (this is the "route Java-side colors through the theme
   system" requirement).
6. Theme-aware `Icons` loader + live icon swap on open toolbars and the browser tree.
7. The generated + audited dark icon set under `src/main/resources/icons/dark/`, and
   the generator tool committed under `tools/`.
8. `View > Theme` menu on `MainWindow`, bound to `ThemeManager`, persisting on change.
9. Automated WCAG AA contrast test over both token palettes; headless FX tests for
   theme switching mechanics.
10. Move the 4 font-only inline `setStyle` calls into a `.mono-text` style class
    (issue: "inline setStyle() calls bypassing the stylesheet").
11. Docs: `docs/SUMMARY.md`, `docs/ARCHITECTURE.md` (new ThemeManager/preferences
    paragraph).

**Out of scope (follow-ups, §8)**

- User-customizable/arbitrary themes; layout redesigns (both excluded by the issue).
- An Options dialog (decision #4).
- Theming native `FileChooser`/`DirectoryChooser` (OS-drawn, follows the OS on its own).
- Window title-bar (stage decoration) darkening — OS-controlled in JavaFX.
- Re-rendering *window/stage* icons (`Icons.stageIcons`, Dock icon) per theme — they sit
  on OS chrome, not on app panels.

## 5. Design

### 5.1 Theme model and manager

```java
package com.fxpgadmin.ui;

public enum Theme { LIGHT, DARK, SYSTEM }

/**
 * Single source of truth for the app theme. All Scenes and Dialogs are registered
 * here; switching the selected theme (or an OS scheme change while in SYSTEM)
 * re-styles every registered live scene immediately.
 */
public final class ThemeManager {
    private static final ObjectProperty<Theme> selected = new SimpleObjectProperty<>(Theme.SYSTEM);
    private static final ReadOnlyObjectWrapper<Theme> effective = ...; // LIGHT or DARK only
    private static final Set<Scene> scenes = Collections.newSetFromMap(new WeakHashMap<>());

    public static void init(AppPreferences prefs);       // FX thread, before first window
    public static void apply(Scene scene);               // add sheets + register
    public static void apply(Dialog<?> dialog);          // apply(dialog.getDialogPane().getScene())
    public static ObjectProperty<Theme> selectedProperty();
    public static ReadOnlyObjectProperty<Theme> effectiveProperty();  // for Icons + tree refresh
}
```

- `effective` resolves `SYSTEM` through `Platform.getPreferences().colorSchemeProperty()`
  with a listener, so OS changes propagate live. `Platform.getPreferences()` must only be
  touched on the FX thread after startup — `init` is called from `PgAdminApp.start`.
- `apply(Scene)` sets the stylesheet list to `[styles.css, theme-light.css|theme-dark.css]`.
  On an `effective` change, iterate the (weak) scene set and swap the second sheet in place.
  Weak set ⇒ closed windows unregister themselves by garbage collection; no leak, no
  explicit unregister call to forget.
- `apply(Dialog)` covers `Alert`, `TextInputDialog`, and plain `Dialog` — their
  `DialogPane` scene exists before `showAndWait()` returns, but to be safe apply on
  `dialog.setOnShowing(...)` if the scene is still null at call time.
- Persistence: a listener on `selected` writes `AppPreferences` — save-on-change, like
  `ServerRegistry`. No DB, no threading concerns (hard rule 1 untouched).

### 5.2 CSS architecture — tokens + two theme sheets

`styles.css` keeps every structural rule (padding, fonts, borders widths, radii) but every
color literal becomes a looked-up color:

```css
.sql-keyword { -fx-fill: -app-sql-keyword; -fx-font-weight: bold; }
.explain-canvas { -fx-background-color: -app-explain-canvas-bg; }
.scratch-pad-header { -fx-background-color: -app-panel-header-bg;
                      -fx-border-color: transparent transparent -app-panel-header-border transparent; }
/* etc. — every hex in today's styles.css gets a token */
```

`theme-light.css` is *only* a `.root { }` block assigning today's exact hex values to the
tokens — zero visual change. `theme-dark.css` assigns the dark palette **and** re-derives
Modena:

```css
.root {
    -fx-base: #3b3f43;                       /* Modena derives most control colors from this */
    -fx-background: #2b2d30;
    -fx-control-inner-background: #1e1f22;
    -fx-control-inner-background-alt: derive(-fx-control-inner-background, 3%);
    -fx-accent: #3574f0;
    -fx-focus-color: #3574f0;
    -fx-faint-focus-color: #3574f022;
    -fx-selection-bar-non-focused: #43454a;
    /* ...then the -app-* tokens, §5.4 */
}
```

RichTextFX needs explicit dark rules (its defaults assume light): `.styled-text-area`
background, `.caret` stroke, `.selection` fill, and the existing `.lineno` background —
all tokenized in `styles.css` alongside the `.sql-*` classes.

### 5.3 Java-side colors → CSS classes (ExplainIcons)

Replace the three `Color` constants with style classes so live diagrams restyle on theme
switch without re-rendering:

```css
.explain-glyph-box    { -fx-fill: -app-explain-glyph-fill;  -fx-stroke: -app-explain-glyph-stroke; }
.explain-glyph-line   { -fx-fill: transparent;              -fx-stroke: -app-explain-glyph-stroke; }
.explain-glyph-accent { -fx-stroke: -app-explain-glyph-accent; }
.explain-glyph-accent-fill { -fx-fill: -app-explain-glyph-accent; }
.explain-glyph-text   { -fx-fill: -app-explain-glyph-accent; }
```

`Shape` and `Text` are both CSS-styleable (`-fx-fill`/`-fx-stroke`), so the change in
`ExplainIcons` is mechanical: every `setFill(FILL)`/`setStroke(STROKE)`/`setFill(ACCENT)`
becomes `getStyleClass().add("explain-glyph-…")`. `Color.TRANSPARENT` stays in code
(`circleOutline`, `padlockGlyph`, `ExplainCanvas.java:176`) — transparency is not a theme
concern. Stroke widths stay in code (structure, not color). Anything CSS-classed inside
`.explain-node` (already the case for node boxes/captions/connectors) needs no Java change
at all.

### 5.5 Theme-aware icons + live swap

- `Icons.image(name)` keys its cache by `(effectiveTheme, name)`; for DARK it tries
  `/icons/dark/<name>.png` first and falls back to `/icons/<name>.png` — a missing dark
  file degrades to the light icon, never to a blank.
- Live update of already-built UI:
  - **Toolbars** (`Icons.toolButton`, 17 call sites across MainWindow, QueryToolWindow,
    DataEditorWindow, ServerStatusWindow): `toolButton` records its `ImageView` + icon
    name in a static `WeakHashMap<ImageView,String>`; a `ThemeManager.effectiveProperty()`
    listener inside `Icons` re-sets each live view's image on switch. Weak keys ⇒ closed
    windows drop out automatically.
  - **Browser tree** (`MainWindow.java:563`): cells fetch through `Icons.image` on
    `updateItem`, so a single `tree.refresh()` from a listener in `MainWindow` re-icons
    the whole tree.
  - `stageIcons` / Dock icon: intentionally not themed (§4 out-of-scope).

### 5.6 Dark icon set generation (decision #1)

A committed one-off tool, `tools/DarkIconGenerator.java` (plain `java` single-file run,
`javax.imageio` only, no app dependencies):

1. For each `src/main/resources/icons/*.png` (skip `pgAdmin3-512.png` and other stage
   icons — §4), read ARGB pixels.
2. Transform per pixel in HSB, preserving alpha: near-neutral dark pixels (saturation
   < 0.25 and brightness < 0.5 — the black outlines and dark text pgAdmin III icons use)
   map to light: `b' = 1.0 - 0.8*b`; colored pixels get a mild lift
   `b' = min(1, b + 0.15)` and slight desaturation `s' = 0.85*s` so saturated mid-tones
   don't vibrate on dark panels.
3. Write to `src/main/resources/icons/dark/<same-name>.png` (RGBA, not palette).
4. Also emit `tools/icon-audit.html`: every light/dark pair side by side on light and
   dark swatches — the review artifact for the audit pass.

The generator gets icons ~90% of the way; the **audit is mandatory** (issue's core
constraint). Any icon still illegible on `#2b2d30`/`#1e1f22` gets hand-corrected (edit
the generated PNG or special-case its transform) and the audit re-run. The tool stays in
the repo so the set is reproducible when icons are added later.

### 5.7 Startup wiring

`PgAdminApp.start`: construct `AppPreferences`, call `ThemeManager.init(prefs)`, then
`new MainWindow().show(stage)` (which now routes its Scene through
`ThemeManager.apply`). Load order guarantees the first frame is already themed — no
light-flash before dark applies.
